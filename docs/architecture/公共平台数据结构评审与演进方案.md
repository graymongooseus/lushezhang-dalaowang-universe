# 公共平台数据结构评审与演进方案

评审日期：2026-09-23。范围：当前 SQLite v7、schema_v7.sql、校验与构建脚本、更新工作流。定位：从个人维护的来源型人物图谱，演进为允许公众投稿、投票、管理员审核的协作资料平台。本文件是设计建议，没有执行数据库迁移或修改线上网站。

## 1. 结论与保留项

当前数据结构可以继续演进，不必重新录入人物。已有稳定人物 ID、任职/教育明细、关系及多条证据、关系时间段、视频片段、亲属索引和操作日志。这些是有价值的基础。

关键改变是把公开知识组织成可引用、可修订的“资料条目”，在其外增加投稿、审核、版本和发布机制。人员规模本身尚不是当前瓶颈；公共写入的权限、并发冲突和发布边界更优先。

建议产品同时提供：人物档案、机构与履历检索、关系图、来源库、修改记录。现有“鲁社长大老王宇宙”保留为专题视图，未来不同节目/来源引用同一人物，不复制人物数据库。

## 2. 实测结果与优先级

当前有 24 张表、103 人物、86 关系、118 关系证据、143 来源、111 任职、17 教育记录、24 人物事件、111 视频片段。SQLite 完整性检查通过，外键异常为 0；全部 86 条关系至少关联一条证据。检查范围是结构和引用完整性，不代表已经逐条核实内容真实性。

| 优先级 | 现状与证据 | 对公共平台的影响 | 最小有效调整 |
|---|---|---|---|
| P0 | `people.name` 有 UNIQUE；校验脚本也禁止同名 | 同名官员无法分别建档 | 姓名改为普通索引，ID 唯一；增加消歧描述、别名表和合并/拆分记录；同名只提示，不阻止 |
| P0 | 24 张表未包含账号、投稿、审核决定、投票或正式版本链；change_log 有 1,328 条但没有操作者字段 | 无法回答谁提议、谁审核、为何批准；更新会覆盖他人修改 | 新增投稿、不可变版本、审核决定；现有日志保留为旧审计，不伪造历史操作者 |
| P0 | `relationships.status` 有 12 种文本，包括“主播说法待核实”和“主播说法，待核实” | 筛选、审核规则和前端样式容易失配 | 稳定状态编码；拆开说法类型、核实状态、审核状态及可见范围；保留旧文案作迁移说明 |
| P0 | education、appointments、person_events 各只有一个 source_id；多来源证据主要在 relationships 中 | 同一任职或学历的支持/反驳资料难统一管理 | 为所有资料条目提供多对多的来源引用，证据精确挂到版本 |
| P0 | export_public.py 用全库复制后删除两张表的数据；build.py 会整表嵌入页面 | 将来新增账号、草稿、内部备注时，沿用该模式可能把非公开数据导出 | 公共输出改成明确字段白名单和已发布视图；应用和数据库两层限制读取 |
| P1 | 86 条关系时间段中 64 条为 undated（74.4%）；任职日期同时存在年/月/日精度 | 时间轴无法把未知时期当成真实长期关系 | 明确未知/已知/持续状态及每个端点的精度，保留发生时间与平台收录时间 |
| P1 | 111 任职覆盖 41/103 人，17 教育覆盖 14/103 人 | 用户会把“未收录”误看成“没有任职/学历” | 按字段展示完整度和补充入口；不把缺失当负面事实，也不强制补造 |
| P1 | 任职中的机构字段有 87 种文本值，无统一机构/职务/地区实体 | 无法可靠检索机构更名、上下级及“同年在同省共事” | 增加机构、职务、地区与历史名称；原字符串保留待映射，未知映射不猜 |
| P1 | 全部人物有 primary_faction_id，其中 80 人指向“派系待定” | 该占位节点容易被误当共同圈子 | “待定”迁为无已收录归属；圈层归属多对多且有时效/出处，不强制每人一个派系 |
| P1 | people.category 与分类关联重复维护；关系类型/分数在关系和时间段重复 | 未来多人编辑时可能出现两个版本的当前值 | 一个权威字段，其他通过视图/生成结果读取；保留七类主分类和头像色环规则 |
| P1 | 5 个视频类型来源中只有 2 个有 video_analyses 行；31/118 条关系证据未填 locator | 旧资料没有全部迁到逐段索引；不是所有引用都能定位到段落 | 给旧资料补迁移任务；网页资料可用章节/页面位置，不能硬套视频秒数 |
| P2 | 当前生成 HTML 7,488,152 字节（约 7.14 MiB），包含全量数据和内嵌图片 | 人物增长后手机首次访问开销持续增加 | 保留离线导出，在线版采用分页 API、局部图谱、独立缩略图及缓存 |

补充：143 个来源中 82 个没有 published_at、5 个没有 URL。书籍或用户维护记录可以没有 URL；未标日期的页面可以没有发布日期。这些需要分类解释，并非全部是错误。当前最高学历/职务指针未发现指向他人的记录，但现有外键并不能防止未来发生这种写入。

## 3. 核心模型：人物、资料条目、证据分别保存

借鉴 Wikibase 的“实体—陈述—限定条件—引用”结构，但继续使用易查询的任职、教育、关系等专用表，避免把所有数据都放进没有约束的 JSON。

### 人物与机构

- `people`：稳定 ID、规范显示姓名、消歧描述、主分类、档案发布状态。保留现有 ID；新增 ID 不从姓名推导。真实公众身份与平台注册账号分开。
- `person_names`：别名、公开笔名、语种、名称类型、来源和适用时间。非全局唯一；不导入字幕错字为别名。
- `external_identifiers`：人物与外部资料库 ID，提供 `(provider, external_id)` 唯一约束。
- `person_merge_events`：合并来源 ID、保留 ID、审核人、理由、时间和所迁关联记录，以便纠错/拆分；旧 URL 重定向，不直接删除旧身份。
- `categories`：七类主分类字典，people 只存主分类 ID；头像颜色只从此表取。职业经历、政治立场及圈层另存。
- `organizations`、`positions`、`places`：机构、职务、地区的稳定 ID；历史名称、上下级归属随时间记录。行政区更名与合并不得覆盖历史。
- `appointments`：人物、机构、职务、管辖地区、任职时间；“现任”按有依据的时间计算，“最高已收录职务”可保留人工选择及理由，不能简单按文本或日期最大值排名。
- `education`：院校机构 ID、学历、学位、专业、学习方式、起止时间。最高学历和最高学位仍分开。

### 资料条目与版本

建议增加公共父表 `statements`（资料条目），让 `appointments / education / relationships / events / memberships` 等专用表共享 `statement_id`。每个条目必须恰好对应其 kind 的专用明细，提交时在服务端和事务内校验类型匹配。

每条资料至少保存：稳定 ID、条目类型、相关人物、当前发布版本 ID。每个版本保存：作者、前一版本、内容、说法类型、核实状态、实际有效时间及精度、创建时间。核心查询字段放关系表；不可变版本快照可使用 JSONB，以便展示差异和回滚。

`statement_revisions` 是修订的来源；已发布的专用明细表是由批准版本同步生成的查询投影，不能再提供一个绕过审核的独立编辑入口。两者在同一事务更新，避免出现两个可写真相。早期不必上复杂事件溯源系统。

拆分四个维度：

| 维度 | 示例 | 含义 |
|---|---|---|
| claim_kind | 公开记录、当事人自述、转述、观点、预测 | 来源在表达什么 |
| verification_status | 未评估、有证据支持、有争议、被反证 | 本平台根据材料作出的核对结果 |
| review_state | 草稿、待审、需修改、批准、驳回、撤回 | 当前修订处于哪一步 |
| visibility | 私有、审核可见、公开、隐藏 | 谁可以读取 |

“批准发布一条主播观点”不等于“证明观点为事实”。现有宇宙专题可以显示这类材料，并保留说话人、出处与说法类型；跨来源人物档案可以选择展示层次。

同一属性允许相互冲突的条目，例如两个来源对入学年份有不同记载。错误版本的修正与真实关系随时间变化必须分开：前者生成修订，后者增加有效时间段。新的说法不能静默覆盖旧证据。

### 来源、定位与附件

- `sources`：来源主体、标题、发布者、语种、来源类型、发布日期、规范 URL、外部视频 ID。
- `source_versions`：抓取/查看时间、版本 URL、可用状态、内容摘要 hash；网页内容变化时保留出处版本。hash 只帮助识别版本，不证明内容真实。
- `source_derivations`：转载、剪辑、转述关系，可多个上游；统计“独立来源”时不能把同篇报道的十次转载当十份证据。
- `source_passages`：视频片段秒数、书籍页码、网页章节等结构化定位，包含定位精度。替代音频与 YouTube 版本分开，映射不精确时继续用章节入口。
- `citations`：条目修订 ID、来源版本/段落 ID、支持/反驳/背景立场、短摘录或原创概述。旧 locator 文本保留，不能无依据地猜成秒数。
- `assets`：头像和附件的存储键、mime、大小、hash、来源、许可、署名要求、公开状态；头像资料从文件 manifest 逐步迁入此表。

第一期优先接受链接和必要短摘录，降低附件处理负担；允许上传时，未审核附件保持私有。公开检索不包含投稿人邮箱、登录信息或审核内部备注。公开署名用用户选择的昵称。

### 事件、关系与时间

- `events` 加 `event_participants`：同一任免/案件可关联多人，各有参与角色，避免每人复制一个矛盾版本的事件。状态变化作用于各参与者，不把一个事件中的所有人都视为被调查者。
- 亲属关系采用稳定类型、方向及逆关系：父母→子女、兄弟姐妹、配偶等；无向关系两端 ID 排序用于去重。关系不同时间/不同来源主张不能被错误合并。
- `kinship_links` 成为已发布、有效、未被替代关系的索引/视图。三步展开保留环检测、上限和未知时间开关；任一步待核，整条路径不提升为已证实。
- 圈层 (`networks`/现 factions) 区分正式组织、共事网络、学术/商业/节目社交圈与分析者提出的政治圈层。共同任职可计算为“共事线索”，不能自动发布成私人友好或政治忠诚。
- 关系强度、亲疏评分必须有评分者、方法、维度和时间；社区投票不要写进 `relationships.strength`，也不要把支持票变成证据可信度百分比。

时间至少区分：现实有效时间、来源发布日期、平台记录时间、批准发布/被替代时间。日期端点保存 `value + precision + state`，state 区分已知、未知、持续；“结束时间未知”不等于“至今”。只知年份可建立用于检索的年份范围，但展示仍是年份，不能补造成 1 月 1 日的事实日期。

默认时间轴回答“用现在收录的资料回看某年”。未来增加知识时间筛选，才可回答“平台在某天已经知道哪些资料”；当前缺失的历史发布时间不补造。

## 4. 投稿、审核、版本、投票

建议早期闭环：游客可浏览；注册用户可投稿、修改自己的草稿、投票；审核员可审稿；管理员处理账号、字典、冲突和撤回。具名本人/官方来源不等于平台注册审核员。

```mermaid
flowchart LR
  A[用户或视频整理工具] --> B[资料草稿与证据]
  B --> C[提交不可变修订]
  C --> D[审核队列与社区反馈]
  D --> E{管理员决定}
  E -->|需修改| B
  E -->|批准| F[事务发布并记录版本]
  E -->|驳回| G[保存理由与记录]
  F --> H[人物档案 / 搜索 / 图谱]
```

最小新增协作表：

| 表 | 作用与关键约束 |
|---|---|
| users / user_roles | 使用成熟认证组件；公开昵称与私有登录信息分开；角色变更留痕 |
| change_requests | 一次投稿；提交人、状态、提交时间、幂等键；一批视频也走同一入口 |
| change_request_items | 本次拟新增/修改/撤回的条目及不可变修订 ID、base_revision_id |
| statement_revisions | 条目版本；同条目 version 唯一；提交后不可原地改，修改生成新版本 |
| review_decisions | 审核人、被审修订、决定、理由、时间；保存每一次决定，不只保存最后一人 |
| votes | 用户、具体投稿修订、维度、票值、时间；`(user_id, target_revision_id, dimension)` 唯一 |
| discussion_comments | 对投稿的讨论；内容编辑/隐藏留记录，可举报 |
| audit_events | 操作者、对象、动作、request_id、时间；应用权限下仅追加，不混同公开修订历史 |

管理员批准时，用事务检查当前版本仍等于 base_revision_id；不一致则进入冲突处理，而不是后提交者覆盖先提交者。事务同时写审核结果、版本发布指针和查询投影。批准重试用幂等键防止生成两条记录。缓存更新在提交成功后触发，可重试。

MVP 默认审核人不审批自己的投稿；如果初期只有一位维护人，应把维护人直接录入明确记录为独立动作，不伪称第二人复核。

投票建议先做“资料有帮助 / 需要补充证据”和审核优先级。按账号每版本每维度一票，可撤销/变更但保留审计；投稿重大修改后重新计票，旧票不继承给新内容。票数不自动通过审核，也不决定事实或给人物的道德评分。初期用简单限频、注册/封禁状态校验即可；不急着设计复杂积分与声望算法。

公共用户不能直接写正式人物表；权限必须在服务器执行，隐藏按钮不是授权控制。Django 的默认模型权限也不自动实现“只能编辑自己的草稿”，须加入对象级检查。若使用 PostgreSQL RLS 作为额外边界，要测试匿名、投稿者、审核者各角色，避免应用以绕过策略的数据库角色运行。

## 5. 前后端和运行架构

建议在线主库使用 PostgreSQL，后端优先 Django，前端使用响应式 Web。现有 Python 代码可复用；Django 自带认证、用户组和管理后台，适合先做审核工具。管理员页面仍需补版本 diff、来源预览、冲突处理和专用审批动作。面向公众的页面使用专门设计的界面。

采用 PostgreSQL 是为在线多人编辑、事务和权限边界做准备，不是因为 103 人规模已经超出 SQLite 能力。迁移前 SQLite 仍是唯一来源；切换时停止旧写入、核对映射，之后 PostgreSQL 成为唯一在线主库，SQLite 仅作导出/离线包，不能两边长期独立更新。

图谱仍由关系表查询生成。初期用 SQL 邻接查询/递归查询完成三步亲属展开，无须立即增加图数据库、消息队列或搜索集群。后续出现可测量的性能需求再扩展。

- 电脑：筛选区 + 图谱/列表 + 侧边档案；每个条目可查看来源和修改历史。
- 手机：列表/人物卡片为默认入口，筛选抽屉，点击进入档案；图谱是按需查看的局部邻居视图。不能依赖 hover，也不在首页绘制全库。
- 第一批筛选：姓名/核对别名、七类主分类、地区、机构、任职年份、职务、学历、事件类型、资料类型/核实状态。当前状态需有有效日期依据，不由单个最新标签推断。
- API 分页返回人物列表；图谱接口接受中心人物、深度、时间、关系类型和节点上限；节点被截断时明确提示。
- 头像独立缩略图、延迟加载和 CDN 缓存；正文与图谱数据不重复下载。
- 搜索先支持中文全名、前缀和已核对别名；中文分词/繁简检索以真实查询集验证，不能直接假设英文全文搜索配置足够。相关记录仍显示规范姓名。
- 公开字段按白名单构建 API/导出，不再以“删掉已知私密表”为策略。未审核草稿和内部资料不能进入客户端 JSON。
- 代码、公开内容、第三方资料和照片许可分别记录；投稿时记录贡献者许可选择和版本，避免把 MIT 自动扩展到所有投稿材料。

## 6. 分阶段实施与验收

**阶段一：数据底座 v8。** 先修姓名唯一约束，统一状态编码，整理分类/圈层、增加来源定位和机构映射；迁移保留旧 ID 和旧值。为旧 3 个视频来源建立补迁移任务。所有不确定映射都进入队列，不直接规范成新的事实。通过重复姓名建档、旧 URL、引用外键、时间未知边界和现有图谱回归。

**阶段二：最小公共平台。** PostgreSQL + 后端认证，完成“投稿一条任职资料→提交证据→管理员审核→公开档案更新→查看历史→回滚”一个闭环；同时提供手机和电脑的列表/档案查询。随后把教育、关系、事件接入同一个流程。验收两人并发编辑、越权请求、重复批准、驳回不公开、草稿不可下载、回滚保留审计。

**阶段三：社区反馈。** 加投票、讨论、举报、关注人物及审核队列排序；验证重复投票、改稿后旧票隔离、封禁用户权限。视频整理/AI 导入也先生成投稿，不能绕过管理员发布。

**阶段四：检索与规模化。** 补时间点检索、来源家族与冲突提示、局部图谱缓存；按实际查询计划增加索引。建立数据库备份和恢复演练，再根据测得的数据量/请求量优化搜索与缓存。

迁移验收保持当前 103 个稳定人物 ID、86 条关系和全部证据关联可追溯。最终记录数若因拆分事件、规范名称或条目版本增加，不强求新旧表行数机械相等；应核对逐条映射、孤儿记录、内容差异及发布可见性。当前未进行并发/性能压测，不能给出容量保证或时间成本承诺。
